## 6. Development hot-reload fix

- [x] 6.1 Added `gem "listen"` to the `:development` group; `bundle install` pulled in `listen` + `rb-fsevent` (macOS evented backend)
- [x] 6.2 Cleared `tmp/cache/bootsnap` (was 232MB, stale from years of old gem versions); regenerated clean at 30MB
- [x] 6.3 **Important correction to the plan's assumption**: adding the `listen` gem alone does *not* switch Rails' file watcher — verified via `Rails.application.config.file_watcher`, which returned `ActiveSupport::FileUpdateChecker` (polling) even with `listen` loaded and `defined?(Listen)` true. Checked Rails 8.1.3 source (`railties-8.1.3/lib/rails/application/configuration.rb:62`): the auto-detection folklore ("just add listen and Rails notices") is not how modern Rails works — `file_watcher` defaults unconditionally to the polling checker; the app must opt in explicitly. Added `config.file_watcher = ActiveSupport::EventedFileUpdateChecker if defined?(Listen)` to `config/environments/development.rb`, confirmed it now resolves to the evented checker. **A/B measured the actual impact**: 20 sequential requests to `/`, polling vs. evented, ~74ms/request vs. ~76ms/request — no measurable difference at this app's size (160 files in `app/`). The fix is still correct (matches Rails' own intent for the `listen` gem, and will matter more as the app grows) but isn't the dominant lever here.
- [x] 6.4 Investigated whether `bin/dev`'s process topology is the real source of "sluggish": confirmed no browser-side live-reload existed — `esbuild --watch`/`sass --watch` rebuild files, nothing pushes the browser to refresh. User asked to fix this. Added `guard`, `guard-livereload`, `rack-livereload` (dev group), a `Guardfile` watching `app/views`, `app/helpers`, `app/assets/builds`, and `public`, `config.middleware.insert_after ActionDispatch::Static, Rack::LiveReload` in `config/environments/development.rb`, and a `livereload: bundle exec guard` line in `Procfile.dev`.
  - **While testing this, found the actual root cause of the original "sluggish/broken hotloading" complaint**: `public/assets/` contained a fully precompiled Sprockets manifest and fingerprinted asset files dated back to March — a leftover from some earlier `rails assets:precompile` run. Because those files physically exist on disk, Rails serves them directly (bypassing live Sprockets compilation) **in development too**, regardless of any source file changes. This means CSS/JS edits could go completely unreflected in the browser even after a full manual refresh — not just "slow," genuinely stuck, until someone thought to delete `public/assets` and restart the server. This is almost certainly what "sluggish hotloading (which was not the point)" actually meant. Deleted `public/assets` (confirmed gitignored, untracked, safe — see `.gitignore:28`) and restarted the server; live compilation resumed immediately.
  - Also found and fixed a second real bug: `guard-livereload`'s default "apply CSS live without a page reload" behavior is incompatible with Sprockets' fingerprinted asset URLs — each content change produces a new digest, so the browser's existing `<link>` tag (pointing to the old digest) 404s instead of picking up the change. Set `apply_css_live: false` in the Guardfile to force full-page reloads instead, which resolved it.
  - **Verified end-to-end via live browser automation** (not just config inspection): booted `bin/rails server`, `bundle exec guard --no-interactions`, loaded the homepage, edited `app/assets/builds/application.css` directly, and watched the browser auto-refresh with the change applied — three times, with three different colors, no manual reload triggered by me.

## 8. Asset pipeline consolidation

- [x] 8.1 Investigated: **the original "redundant pipeline" hypothesis doesn't hold up.** Checked what actually serves the app's own CSS — the homepage's `<link>` tag points at a Sprockets-fingerprinted URL (`/assets/application-<digest>.css`), confirming `sprockets-rails` is genuinely serving/fingerprinting `app/assets/builds/application.css` (the `cssbundling-rails`/dart-sass CLI output) for the whole site, not just for ActiveAdmin. Separately, `sassc-rails` is what compiles `app/assets/stylesheets/active_admin.scss` — ActiveAdmin ships Sprockets/Sass-oriented SCSS partials, and `sassc-rails` is the only Sass processor registered with Sprockets in this Gemfile (confirmed via `Gemfile.lock`: no `sass-rails`, no `dartsass-rails`, no `propshaft`). Both gems are load-bearing for distinct, legitimate purposes — this isn't two competing systems doing the same job, it's `sprockets-rails` fingerprinting everything and `sassc-rails` being the one thing that can compile ActiveAdmin's own SCSS.
- [x] 8.2 **No change made.** Removing either gem would break something real (whole-site asset fingerprinting, or `/admin` styling) for no gain. Migrating off Sprockets entirely (e.g. to Propshaft) would be the actual "real" consolidation, but that's a materially bigger, riskier change than this tune-up's scope — noted as a legitimate future follow-up, not attempted here.
